# base_yaw 与 t7 那个「0/200 可解」

> 状态：**已解决**（2026-10-11）。方案 A 已实施，见第 7 节。
> 起因：`matlab/checks/t7_ik_matlab.m` 报「RST 可解 0/200」，而 `t9_ik_truth.py` 说 320/320 全解。
>
> ⚠️ **更正**：本文最初把 t7 的失败归因于「基准系差 90°」。**那个归因是不完整的** ——
> 基准系确实错了（本文第 1~3 节的测量都是真的），但它不是让 t7 归零的原因。
> 真正让残差变成 390 米的，是一个**单位错误**（mm 当成 m 喂给 `inverseKinematics`），
> 见第 6 节。基准系问题掩盖了这个单位错误。

---

## 0. 一句话

**`armSpec` 里没有「臂装在车上的朝向」这个信息**，而网页里有（`MODEL.base.yaw = -90`）。
所以 MATLAB 算出来的位姿和网页算出来的，差一个绕 Z 轴 90° 的旋转 —— 谁也没错，
是两个「基准系」没对齐。

---

## 1. 「base_yaw」到底是什么

它**不是关节**，是**安装朝向**：这条臂以什么方向焊/拧在底盘上。

同济臂的例子：臂的本体「前方」是 +Y，但整车定义「前方」是 +X，
所以装的时候要**绕竖直轴转 90°** 才对得上。这就是 `yaw = -90`。

- 它**不影响臂自身的运动学**：同一组关节角 `q`，各杆之间的相对姿态一模一样
- 它**只影响**「臂的姿态」和「整车/任务坐标系」之间的换算
- 所以它既像模型的一部分（换个朝向就是另一台机器），又像"使用时的参数"（同一台臂装到别的车上就变）

**这就是为什么它会成为一个需要拍板的问题。**

---

## 2. 现状：两边各有一套"基准系"，而且不一样

| | 网页 JS | MATLAB |
|---|---|---|
| 定义在哪 | `MODEL.base = {xyz:[0,0,0], yaw:-90}` | **没有** —— `armSpec` 的字段只有 `name/joint/type/axis/offset/limits/rot` |
| 谁在用 | `01-kinematics.js` 的 `buildChain()` / `fkAll()` 第 116 行：<br>`let R = rotZdeg(MODEL.base.yaw)` | `buildChain.m` **直接把 `robot.Base` 当整机原点**，不施加任何旋转 |
| 效果 | 正解结果在「**整车系**」 | 正解结果在「**臂底座系**」 |

**实测**（我跑了一次探针，同一组 `q` 在两边各算一次末端位置）：

```
 idx |  JS 位置 (mm)                    |  MATLAB 位置 (mm)
  0  | [   471.0    -85.5    476.5 ]   | [    85.5    471.0    476.5 ]
  1  | [   -50.5   -445.0    632.5 ]   | [   445.0    -50.5    632.5 ]
  2  | [   103.5    605.8    435.1 ]   | [  -605.8    103.5    435.1 ]

JS == Rz(yaw) * MATLAB    ->  最大偏差 0.0000 mm    ← yaw = -90°
JS == Rz(180) * MATLAB    ->  最大偏差 869.2 mm
```

⇒ 两边**恰好差一个 `Rz(-90°)`**，干净利落，没有别的误差。

---

## 3. 为什么 `t7` 会错

`t7_ik_matlab.m` 想「用 MATLAB 的 RST 独立复核网页那份 IK」，于是它要自己把
任务域坐标换算到臂的基准系。它手写了一个映射：

```matlab
function p = taskToBase(p), p = [-p(1), -p(2), p(3)-170]; end   % 第 60 行
```

但这个映射是 `Rz(180°)` 那一类，**和实测需要的 `Rz(-90°)` 对不上**。
目标点从一开始就摆错了位置，于是：

- 200 个位姿的 RST 位置误差全部落在 **364~594 mm**（中位 482 mm）
- 这是**系统性偏差**，不是「求解器解不出来」
- 结果「0/200 可解」是**假的**，不能拿它当结论

**注意**：`t7` 错在"换算"，不在"求解"。把它当成"RST 说这臂做不到"会得出完全相反的结论。

---

## 4. 两条路，要先拍板选哪条

### 方案 A：承认 `base_yaw` 是模型的一部分

给 `armSpec` 加 `base` 字段（`xyz` + `yaw`），让 `buildChain.m` 也施加这个固定旋转。

- ✅ MATLAB 与网页**语义完全一致**，以后任何交叉验证都不用再手写坐标换算
- ✅ 能表达「这条臂是斜着装的车」这件事；现在的 `armSpec` 表达不了
- ⚠️ 会**改动 `buildChain` 的正解结果**（整体转 90°）。所有依赖"MATLAB 位置 =
  臂底座系"的地方都要跟着复查：`t4_dump_check`、`t0_probe`、`t7`
- ⚠️ 要跟 `RULES` 里的换算（`base.X=-OXYZ.Y` 那一套、`baseH=170`）对齐，
  别变成"转了两次"

### 方案 B：`armSpec` 只管臂，朝向留在"使用层"

保持 `armSpec` 是纯臂定义，把 `base_yaw` 当成"整机安装参数"，
由需要它的地方（`t7`、以后可能的整机工具）自己施加。

- ✅ `buildChain` 不动，没有回归风险
- ✅ 概念上更干净：「臂」和「臂装在车上的哪一面」是两件事
- ⚠️ 每个跨界的脚本都要自己记得转一次 —— **这正是 `t7` 踩的坑**，
  方案 B 不改机制的话，同样的错误还会再犯
- ⚠️ 网页那边 `MODEL.base` 是**存在模型 JSON 里**的（`读取文件` 会带进来），
  所以"朝向不进模型"和网页的现状也不一致

---

## 5. 我的倾向（仅供参考，不替你决定）

**倾向 A**，但理由不是"省事"：

1. 网页那边 `base.yaw` **已经**是模型 JSON 的一部分了（导出/读入都带着），
   MATLAB 侧不认它，等于两边对"模型"的定义就不一样 —— 这是**语义分裂**，不只是路径问题。
2. 实测差别是**干净的单一旋转**，说明这不是"两套算法"，就是"同一个模型少了个安装参数"。
3. 方案 B 靠"每个脚本自己记得转"，而 `t7` 已经证明了**人会忘**。

但 A 有个必须先回答的问题：**`armSpec` 加了 `base` 之后，`RULES` 里那套
`base ↔ OXYZ` 的换算还算不算数？** 两处都在描述"臂和整车的关系"，
不澄清就会变成转了两次。这个得你按比赛规则手册的口径定，我不敢替你拍。

## 6. ★ 真正的元凶：单位错误（mm 当 m）

在动手改基准系之前，先把 `t7` 的目标点直接喂给 RST 的 `inverseKinematics` 试了一下，
结果**残差 390490 mm** —— 而目标距离原点是 390.5 mm。**比值正好 1000。**

```
 t7 目标 Eb (mm)              RST 解出来的位置 (mm)         残差
 [ 15.6 -178.2  348.2]   ->   [ 31.3 -415.2  886.4]      390490.5
 [ 61.9 -242.7  330.8]   ->   [135.4 -535.8  800.5]      413944.1
```

`inverseKinematics` 的目标位姿单位是**【米】**，而 `t7` 把毫米直接塞进了
`Tt(1:3,4)`。等于把目标点放到 390 米外 —— 求解器只能回 `best available`，
位置误差恰好是 1000 倍。

**为什么这个 bug 以前没被发现**：因为基准系差 90° 这件事先把水搅浑了。
当时的推理止步于"两边差一个 Rz(−90°)，所以目标摆错了 0.5 米"——
**0.5 米这个量级太像"摆错位置"了，没人再去核对数量级**。
实际上目标点从来没被正确送到求解器手里。

**教训**：一个显眼的错误会掩盖另一个更大的错误。定位问题时，
"这个偏差的量级对不对"应该先算一遍 —— 390490 / 390.5 = 1000 是个一眼就能看出的破绽，
但当时被"差 90°"这个合理解释带过去了，没有做这个除法。

## 7. 实际怎么解决的（方案 A，已实施）

**基准系**：安装朝向进了树，两边统一。

| 改了什么 | 文件 |
|---|---|
| 新增 `armBase()`：yaw / baseH / taskMap 的唯一真源（对应网页 `configs/tongji.js` 的 `rules.frame`） | `matlab/model/armBase.m` |
| `buildChain` 把 `base.yaw` 当**根部固定变换**加进树（对应网页 `buildChain()` 的 `rotZdeg(MODEL.base.yaw)`） | `matlab/model/buildChain.m` |
| 新增 `taskToBase` / `baseToTask` / `dirToBase` / `taskMapPhi`，与网页 `mapObj()` 同一套公式 | `matlab/model/` |
| 删掉 `t7` 里手写的 `taskToBase`/`dirToBase`（局部函数会**遮蔽**库函数，必须删） | `matlab/checks/t7_ik_matlab.m` |
| `armFeasData` **去掉**手动 `Rz` —— yaw 已进树，再做一次就是转两次 | `matlab/core/armFeasData.m` |
| `t2_app_smoke` 的 cfg.base 改用 `armBase()`，并把"累积 offset""杆方向解码表"等断言改成在基座系里做 | `matlab/checks/t2_app_smoke.m` |
| **单位修掉**：`Tt(1:3,4) = Eb(:)/1000`，误差也换回 mm | `matlab/checks/t7_ik_matlab.m` |

**验证**：`t2_app_smoke` 全过，其中 `chainFK vs RST getTransform` 位置差 **6.4e-14 mm**；
MATLAB 与网页的零位末端位置现在**逐位相同**（都是 `[471.0, −85.5, 476.5]`）。

**t7 修好前后的实测对比**（同一份 `t7_ik_js.csv`，200 个三级任务域位姿）：

| | 修之前 | 修之后 |
|---|---|---|
| RST `inverseKinematics` 可解 | **0/200 = 0.0%** | **199/200 = 99.5%** |
| RST 位置误差中位 | 481.07 mm | **0.00 mm** |
| 只在 RST 里可解 | 0 | **33**（说明网页那份自写 IK 漏解） |

这与 `t9_ik_truth.py` 的**独立**求解器（Python FK + scipy 信赖域，320/320 = 100%）
互相印证 —— 三套实现现在说的是同一件事：**这些位姿基本都到得了**。
`t9_IK诊断报告.md` 里"没有任何位姿是真解不出来的"这个结论，至此有了第二个独立来源。

**"会不会转两次"这个担心是真的**，而且我在改造中确实踩了：
`armFeasData` 里原来有一段手动 `Rz`，`buildChain` 加了 yaw 之后它就变成第二次旋转，
表现是 `chainFK vs armFeasData` 差 677mm。**凡是"树的根已经含朝向"的地方，
都不能再手动补一次** —— 这条已写进 `armFeasData.m` 和 `t2_app_smoke.m` 的注释。

## 8. 复盘：两个 bug 叠在一起，为什么难查

`t7` 归零是**两个独立错误**共同造成的，而且一个掩盖了另一个：

1. **基准系不统一**（第 1~3 节）：目标点整体旋转错误。
   症状是"误差约 0.5 米"，量级看着很合理 —— 像"位置摆错了"。
2. **单位错误 mm/m**（第 6 节）：目标点被放大 1000 倍。
   症状本该是"误差 390 米"这种一眼假的数字，但**被第 1 条那个 0.5 米的解释覆盖了** ——
   当时并没有把 390490 这个残差单独拿出来看一眼。

正确的排查顺序本该是：**先看残差的绝对量级**。
390490 mm = 390 米，而整条臂只有 1 米长 —— 这个数本身就该立刻报警。
先做这个除法，能省掉一整轮"基座系差 90°"的推理。

**教训：定位数值问题时，先算"这个偏差有多大、本该有多大"，再去找原因。**
"两边差一个固定旋转"这种解释很容易让人满足，从而跳过量级核对。
